# 三层混合判断架构

食物寒热属性的判定分三层，置信度递减，来源可追溯。

```
用户口述
   ↓
┌─────────────────────────────────────────────┐
│ 第一层 硬规则库          confidence 0.9      │
│   food_properties.json 规范名精确命中         │
│   直接查表，表值即权威，不叠加模型猜测         │
├─────────────────────────────────────────────┤
│ 第一层附 食材变体层       confidence 0.9      │
│   条目自带 variant_nature（如 红薯→烤红薯 温）│
│   查表直取，优先于通用烹饪修正                 │
├─────────────────────────────────────────────┤
│ 第二层 组合推理（烹饪修正） confidence 0.6    │
│   未精确命中规范名时才生效                     │
│   蒸煮 0 / 煎炸 +1 / 烧烤 +1 / 辛辣 +1 / 冰镇 -1│
├─────────────────────────────────────────────┤
│ 第二层附 温度前缀层       confidence 0.6      │
│   「冰啤酒」「热牛奶」的冰/热用**纯字符串规则**识别 │
│   剥掉前缀后须是完整表内食物名才生效            │
├─────────────────────────────────────────────┤
│ 第三层 LLM 推测          confidence 0.3      │
│   表里没有 → 保留模型判断但标记未验证          │
│   完全判不出 → unresolved / 0.1              │
└─────────────────────────────────────────────┘
   ↓
逐项写入 verification{source, confidence, unverified, detail}
   ↓
接口返回 → 前端按阈值决定是否显示、是否标注
```

## 四性数值编码

```
寒 = -2   凉 = -1   平 = 0   温 = +1   热 = +2
```

溢出夹取：性热的羊肉再油炸仍是热（`clamp` 到 +2），不会出现"超热"。

**unknown 没有值（返回 `None`），不是 0**——否则"未判定"会被当成平性参与运算。

## 两层修正的顺序（不可颠倒）

1. **食材变体层**：条目自带的 `variant_nature` 直接取值，如「可乐」在 `cold` 下为「寒」。
2. **烹饪修正层**：仅当名称**未精确命中**表内规范名时生效，±1 兜底。

为什么不能颠倒：表里精确的变体值会被通用规则破坏。

**为什么"精确命中"要比较名称整体而不是命中词**：`炸馒头` 靠关键词"馒头"识别、
`冰啤酒` 靠包含关系识别，它们的名称与规范名不同，属于"带烹饪信息的派生名称"，
应当让烹饪层生效；而 `希腊酸奶` 名称与规范名完全相同，表值即权威。

## 第二层合成算法（多样食材）

规则由使用者确认，实现在 `nature_math.combine`：

1. **取绝对值最大者为主导项**；同向项累加，**封顶 ±2**；
2. **反向项只做 50% 抵消，不翻转主导方向**（`dominant + 0.5×反向和`，再按主导方向夹到同号）；
3. 平性（0）既不贡献方向也不稀释——加米饭不会把凉性拉平；
4. 并列时取先出现的（通常是主料），保证同样输入结果稳定；
5. **烹饪修正最后叠加**。

示例：
- `番茄(-1) + 鸡蛋(0) + 炒(0)` → -1 → **凉**
- `羊肉(+2) + 苦瓜(-2)` → 2 + 0.5×(-2) = 1 → **温**（不翻转成寒凉）
- `凉(-1) + 温(+1)` → -1 + 0.5 = -0.5 → **凉**（不翻转）

## 温度前缀层（纯规则，不经过模型）

**为什么单独做一层**：模型给的 `cooking` 无法区分"可靠证据"与"猜测"——
它会给出「希腊酸奶=cold」「火腿三明治=grilled」这类没有依据的值。
而「冰啤酒」「热牛奶」里的"冰/热"本身就在名字里，是字符串层面的确定信号。

### 单一入口

温度判定**只有一个函数**：`nature_math.resolve_temperature(name, note)`。
新增前缀只改一处（`CHILL_PREFIXES` / `HEAT_PREFIXES`），
解析层与提示词层都通过它拿结论，不各写一套判断。

> 此前的教训：提示词层曾自己用子串匹配（`"冰" in text`）判断，
> 而解析层用前缀匹配，两套逻辑会漂移——「冰淇淋」在解析层被正确排除，
> 在提示词层却会被当成冰镇。现已统一。

它返回结构化信号（不是文案），所以两种用途都能直接用：

```python
class TemperatureSignal(NamedTuple):
    delta: int        # -1 降温 / +1 升温
    prefix: str       # 命中的前缀，如"冰镇"
    stripped: str     # 去掉前缀后的净名字
    from_field: str   # "name" 或 "note"
```

上层有两个薄包装，区别只在准入严格程度：

| 包装 | 用途 | 准入校验 |
|---|---|---|
| `food_lookup.resolve_temperature_fields` | 解析（决定属性） | 剥后须能锚定到表内条目 |
| `food_lookup.temperature_signal` | 提示词（泛化提醒） | 不做锚定，只要能识别即可 |

### 双通道扫描

| 字段 | 匹配方式 | 为什么 |
|---|---|---|
| **食物名** | 只认**开头**的温度词 | 避免「冰淇淋」「凉皮」「热狗」被误判——它们的温度字是菜名的一部分 |
| **备注** | 在**任意位置**查找 | 备注通常就是"去冰""冰镇""热的"这类短描述，位置不定（实测模型会输出 `note=去冰`） |

优先级：**食物名 > 备注**。名字是用户最直接的表达，备注只在名字没给出温度信息时采信。

### 准入条件（本层最关键的安全边界）

温度来自**食物名**时，剥掉前缀后剩下的词必须是完整表内食物名：

| 输入 | 剥后 | 锚定成功？ | 结果 |
|---|---|---|---|
| 冰啤酒 | 啤酒 | ✅ | 凉 -1 → **寒** |
| 热牛奶 | 牛奶 | ✅ | 平 +1 → **温** |
| 冰红茶 | 红茶 | ✅ | 温 -1 → **平**（冰红茶不是凉茶） |
| 去冰奶茶（note） | — | ✅ 名字锚定 | 平 -1 → **凉** |
| 冰淇淋 | 淇淋 | ❌ | 温度字属于菜名，**不叠加** |
| 热狗 | 狗 | ❌ | 落到表外 → LLM 推测 |
| 热干面 | 干面 | ❌ | 靠关键词命中「面条」，**不升温** |
| 常温奶茶 | 常温不是温度词 | — | 不修正，保持平 |

前缀表见 `app/domain/nature_math.py`，测试见 `tests/test_temperature_layer.py`（48 项）。

### 与表内条目的协同

模型对同一道菜的命名不稳定（「去冰奶茶」可能输出为
`name=去冰奶茶` / `name=奶茶,note=去冰` / `name=冰奶茶`）。
前两种由温度层覆盖，第三种名字不在表内会落到 LLM。
因此**常见温度变体也直接收录进表**（冰奶茶 / 去冰奶茶 / 热奶茶），
两层互为兜底。

## 置信度阈值

| 来源 | 置信度 | 界面行为 |
|---|---|---|
| 表命中且**已审核**（`approved`） | 0.9 | 不标注 |
| 表命中但**待审核**（`pending`） | 0.9 | 标「待验证」 |
| 组合推理 / 烹饪修正 | 0.6 | 标「待验证」 |
| 审核不通过（`rejected`） | 0.6 | 标「待验证」 |
| LLM 推测 | 0.3 | 标「待验证」 |
| 无法判定 | 0.1 | 标「待验证」+ **不显示**寒热属性 |

整餐把握度 = 逐项置信度均值，不再采信模型自报的 `confidence`。

## 审核状态（三态）

`reviewed: false` 无法区分"还没审"和"审了但不认可"，所以用三态：

| 状态 | 含义 | 效果 |
|---|---|---|
| `approved` | 已审核通过 | 真·硬规则库，不标注 |
| `pending` | 待审核（默认） | 高置信度但必须标注 |
| `rejected` | 审核不通过 | 降为组合推理档，不再作硬规则 |

当前表内 147 条全部为 `pending`，所以**界面会普遍显示「待验证」标记**——
这是刻意的：标记密度就是审核进度的可见反馈。


## 已知局限（重要，不要误当 bug 修）

1. **规范名精确命中时，不叠加模型给的烹饪修正。**
   因为无法从模型输出可靠区分"可靠证据"与"猜测"——模型可能给「希腊酸奶」一个
   `cold`、给「火腿三明治」一个 `grilled`，照单全收会把表值污染成错误档位。

   > 这一局限已由**温度前缀层**部分解决：「冰啤酒」「热牛奶」这类温度信息
   > 改用纯字符串规则判定，不再依赖模型。剩下的煎炸/烧烤类修正仍受此限制，
   > 需要时应在表里为该食物单列条目并写 `variant_nature`。

2. **关键词子串会把无关名称拉进表。**
   例如「某个沙拉卷」含"沙拉"→ 判为表内「沙拉」。「薯条」曾被匹配到
   「炸鱼薯条」、「寿司」曾被匹配到「生鱼片」。已通过三级匹配优先级
   （精确同名 > 包含关系按 gap 最小 > 关键词）修掉已知案例，
   但字符串匹配本质上无法完全消除这类歧义。要彻底解决需要菜品别名库或分词。

3. **第二层组合推理尚未接入主流程。**
   `combine()` 已实现并测试，但 `resolve_food` 目前只做单食材判定。
   「番茄炒蛋」这类整菜名要么表里收录，要么整体落到第三层。

4. **第一层数据尚未人工审核。**
   `data/food_properties.json` 全部为 `pending`。属性依据中医饮食养生通行表述整理
   （食物偏性，非药物功效），**上线前应由具备资质的中医师/中药师复核**。
