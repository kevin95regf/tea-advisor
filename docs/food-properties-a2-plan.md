## 2. ① 酱油：项目「平」 vs 来源「温」

### 2.1 现状与证据

- 项目值 `nature: neutral`（平）；来源是 `docs/food-properties-sources.json` 的
  `mapping_review`：映射「酱油 → 酱」**可用**，基准是 `50 号文件 §5.3 别名索引（纲目 9948（辛，温））`，
  语料值 **温**。登记表 `layer=②`、`status=冲突`。
- 强度规则：`50 号文件 §5.4` 自定「**仅经典有载、教材无（不得当教材用）**」。登记表据此记：
  「经典层强度不足以把项目值「平」改成「温」，故 nature 不改，单列待确认」。
- 与「制品不得继承原料四气（§5.2）」**不冲突**：来源条目是「酱」（同为发酵调味品），不是「大豆」，
  不存在「拿原料的四气套制品」这个问题。
- 影响面：`jiangyou` 命中时是 `exact_name_hit`（用户说「酱油」= 条目规范名）→ **查表直取，不走烹饪修正层**；
  四气也不参与任何护栏运算（B1 已取证：四气只影响提示词里的描述与规则层的 `overall_nature`，
  而 `overall_nature` 由 Agent1 给出，不读表）。⇒ 改或不改，**功能上无差别**，差别只在「对外呈现的值是否有据」。

### 2.2 选项

| 选项 | 内容 | 代价 |
|---|---|---|
| **(a) 维持「平」（建议）** | 值不动，补 `note` 留痕，sources 里把「映射采纳」与「值不改」分开写清 | 界面显示「平」，而唯一来源说「温」——靠 `note` 与核验单交代 |
| (b) 改「温」 | 与唯一来源一致 | 违反 §5.4 的强度规则（经典层当教材用）；且项目值「平」会失去任何书面依据 |
| (c) 继续挂「待确认」 | 不改、也不给结论 | 核验单会永久显示「⏳ 待确认」，审核人无法收口；A2 永远关不掉 |

### 2.3 建议落地动作（走正规通道，不手改 JSON）

1. `core/scripts/patch_food_table.py` 的 `ENTRY_FIXES` 增加 `jiangyou`：
   `note` = 「口径分歧：项目值平；《本草纲目》「酱」（§5.3 索引，纲目 9948）记辛、温。经典层强度不足以改判（§5.4），保留项目值。」；
   `review_note` = 「加 note 留痕（口径分歧，经典层）」，格式与 `baicai`/`huanggua`/`lianou` 一致。
2. `docs/food-properties-sources.json` 的 `jiangyou`：
   `mapping_review.accepted` → `true`（**映射**采纳），`reason` 写明「映射可用；来源强度不足以改值，值保留项目「平」」，
   `note` 记结论与日期，`open_question` → `null`。
3. ⚠️ **连带必改**：`core/tests/test_food_review_sheet.py:349` 的 `assert rejected and pending`
   会**变红**（登记过 `mapping_review` 的 18 条里，`jiangyou` 是唯一 `accepted is None` 的一条）。
   这条断言本身是**数据快照式**的
   ——「真实数据里必须存在一个待确认例子」，正是本项目列为反面模式的那种（数据一补齐就红，
   且分不清「数据坏了」还是「活儿干完了」）。改法：保留两个循环（不变式），把最后一句换成
   **负控制** —— 喂合成数据（`accepted=False` 但 `layer=①`／`accepted=None` 但 `layer=①`）断言它被报出。

## 3. ② 金针菇 / 杏鲍菇 / 平菇（+ 新发现的口蘑）

### 3.1 问题是什么

这 3 个词现在挂在 `mogu` 的 `aliases` 与 `keywords` 上，而 `mogu` 在 2026-09-17 的 ④-4 修复中
**由「蘑菇/平」收窄为「蘑菰/寒」**。于是这 3 个词的四气**跟着从「平」静默变成「寒」**——
而 50 号文件对它们**根本没有条目**（③ 无源）。

> 值得写明：**这个变化是我方修复的副作用，不是任何来源的结论。** 修复前它们拿「平」同样无据，
> 但修复后它们拿到的「寒」是「蘑菰」这个**另一个物种**的值。

### 3.2 三个选项与代价

| 选项 | 做法 | 代价 / 后果（含代码取证） |
|---|---|---|
| **(A) 暂留现状** | 不改 | 这 3 个词继续按「蘑菰 = 寒」判定；置信度 **0.9**（`food_lookup.py:467`，因为表内命中）、四气显示为「寒」、`unverified=True` 仍会进「未经验证」节。⇒ **一个无来源的四气以 0.9 置信度呈现**。另一种说法：用户看到的 `detail` 会写「（由「金针菇」识别为「蘑菇」）」，算半留痕 |
| **(B) 各自独立成条** | 新增 3 条 `jinzhengu`/`xingbaogu`/`pinggu` | 撞**两条成文规则**：① `patch_food_table.py:135`「`NEW_ENTRIES` 只用于修矛盾，**不用于补缺口**——无来源的新食材不在这里加」；② `_meta.purpose`「表里没有的条目**必须填 unknown，禁止猜**」→ 新条目要么**造一个无源四气**（直接违规），要么填 `unknown`，而**全表 147 条无一例 `unknown`**，会新开一种状态（连带 `test_every_entry_has_a_known_nature`、`NATURE_LABELS` 渲染、统计口径）。⇒ **本方案认为 (B) 当前不可行**，除非先单独立项定「无源条目怎么表示」 |
| **(C) 从两处移除（建议）** | `aliases` 与 `keywords` 各删这 3 个词 | 3 个词变「表未覆盖」→ 走 `food_lookup.py:352-376`：模型给了四气则 `source=llm`/置信度 **0.3**/未验证；模型也判不出则 `unresolved`/**0.1**。用户输入这 3 词**不再命中表**，显示从「待验证 90%」变「模型推测 30%」。与 `_meta.purpose` 的「不猜」口径一致：**表里不收的词，由模型给推测值并明确标未验证**（这正是三层架构的设计） |

### 3.3 ⚠️ 实施细节（两条都容易踩）

1. **必须两处都清**：`food_lookup.py:286` 把 `keywords` 与 `aliases` **合并后**扫描。
   `docs/food-properties-batch2-confirm.md` 里 (B) 选项写的「移除 `keywords` 后……落到 unknown」
   **只删一处无效** —— 该文档这条措辞要一并修正（本方案 §6 已列）。
2. **必须同步 `patch_food_table.py` 的 `mogu.ENTRY_FIXES`**：它是**声明式强制写入**
   （`patch_food_table.py:185-193`，值不等就覆盖）。只改数据不改它，**下次运行会把 3 个词写回来**，
   而且脚本还会打印「条目修正：…（看起来正常）」，属于静默回滚。

### 3.4 新发现：`口蘑` 与这 3 个词同类，但没进 A2 名单

`mogu` 的 `aliases` 里还有一个 **`口蘑`**：它既非蘑菰、也非香蕈，属于另外的物种（蒙古口蘑一系），
而 `docs/food-properties-sources.json` 的 `mogu` 条目里**没有任何一条 evidence 指向「口蘑」**
（只有「蘑菰」与「香蕈」两条）。⇒ 状态与那 3 个词**完全相同**（③ 无源），只是当初列 A2 时漏了。

**建议**：与这 3 个词**同批裁决**（一起 (A) 或一起 (C)）。若你有相反的专业判断（认为「口蘑」在通行
饮食语境里就是「蘑菇」的同义口语），那就该把它**登记进 sources 的 evidence 里并写明依据**，
而不是留在「无 evidence 却挂在别名上」的状态。

### 3.5 建议落地动作

1. 走 `patch_food_table.py` 的 `ENTRY_FIXES` 改写 `mogu.aliases` / `mogu.keywords`（同时删 3 词或 4 词），
   并把 `review_note` 改成「拆条后收窄为蘑菰；金针菇/杏鲍菇/平菇（+口蘑）无来源，已移出别名，走模型推测路径」。
2. 重跑脚本两次：第二次必须报「**条目修正 0 处**」（幂等验收）。
3. 加一条**数据守卫**（派生不变式 + 负控制）：这 3（或 4）个词**既不在任何条目的 `aliases`、
   也不在任何条目的 `keywords` 里**；负控制喂一份把它们挂回 `aliases` 的合成数据，断言守卫报错。
4. 若选 (A)：把代价写进 `food_properties.json` 的 `_meta.known_limitations` 或 `mogu.review_note`，
   避免「文档没写、数据又是无来源值」的灰区。

## 4. ③ 蘑菇拆条的收尾

拆条本身已完成（`mogu` 收窄为蘑菰/寒，新增 `xianggu`/平，由 `patch_food_table.py` 的
`ENTRY_FIXES` + `NEW_ENTRIES` 落地）。剩三件事：

### 4.1 「`xianggu` 该不该继承原 `mogu` 的审核痕迹」

**实测结论：当前没有痕迹可继承。** 全表 147 条 `review_status` 全是 `pending`、**无一条 `reviewed: true`**，
`reviewed_by` / `reviewed_at` 全为 `null`。所以「继承/不继承」在今天的取值上**没有差别**。

真正该继承的是**留痕**（叙述性字段），而两条都已具备：`mogu.review_note` 写了拆条过程，
`xianggu.review_note` 写了「由 mogu 拆出（④层矛盾）」。

⇒ **建议**：把「不继承，按新条目从零开始」写成**明确结论**（写进 sources 的 `mogu.note` 或
`_meta.mapping_review`），并把 sources 里 `mogu.open_question`（「拆成两条，还是保留一条？」）
**关掉** —— 它已经过期，留着会让后来人以为还没定。

### 4.2 「`mogu` 的 `name` 要不要从「蘑菇」改成「蘑菰」」

**代码取证（这是决定的关键）**：`food_lookup.py:391` 的 `exact_name_hit` 拿「输入整体」与「条目 `name`」
比对；命中才走 **:404 查表直取**，否则走 **:409-430 烹饪修正层**。

| 方案 | 后果 |
|---|---|
| **(i) 保持 `name`「蘑菇」（建议）** | 零行为变化：用户说「蘑菇」「炒蘑菇」仍走查表直取，显示名是熟悉的「蘑菇」。物种归属（条目代表的是蘑菰）写进 `note` 交代 |

## 5. ④ C 组 4 条来源值的限定写法

### 5.1 现状：限定只活在 `how` 里，且 `how` 不渲染

3 条已采纳的 C 组条目各带限定：

| id | `how` | `mapping_review.reason` 里的关键句 |
|---|---|---|
| `shengcai` | 等价名（**叶用变种**，参照莴苣） | 同种不同栽培变种（叶用生菜 vs 教材「莴苣」条的茎用为主）；气、味双项全对应 |

**问题 2**：`how` 的取值**不是受控词表**。实测取值 7 种，其中 `别名/等价名`（4 条）**语义不明**
（到底算别名还是等价名？），A 组 3 条是「正名（药典收载名）」，C 组 3 条各带自由文本限定。

**问题 3**：`tier` 也有同样毛病 —— `_meta.source_registry` 定义的档位只有 4 个值
（`官方` / `通行·教材` / `通行·经典` / 无），而条目的 `evidence[].tier` 是自由文本，
出现 `官方·药典`、`官方·目录(仅身份)`、`通行·教材(有冲突)` 等**不在注册表里的值**。

### 5.2 建议：给 `how` / `tier` 定受控词表（只改措辞，不改任何判定）

| 字段 | 允许取值 | 说明 |
|---|---|---|
| `how` | `正名` ｜ `正名（药典收载名）` ｜ `别名` ｜ `等价名（<限定>）` | 取消 `别名/等价名` 这个混用值：属别名就写 `别名`，属等价名就写 `等价名（…）` |
| `等价名` 的 `<限定>` | `叶用变种` ｜ `省略作物名前缀` ｜ `通称差异` | 现有 3 条正好各占一个；新增等价名映射必须先想清限定词，否则不得标「等价名」 |
| `tier` | `官方·药典` ｜ `官方·目录(仅身份)` ｜ `通行·教材` ｜ `通行·教材(有冲突)` ｜ `通行·经典` | 与注册表的 4 档**显式对应**：注册表给强度档，条目给「档 + 限定」；把这条对应关系写进 `_meta.mapping_rules` |

**另外三条纪律（与既有口径一致，写下来即可）**：

1. **等价名必须同时满足三件事**：`how` 带限定、`reason` 写明「**若否定该映射，该条目落到哪一层**」、
   若限定对用户重要（如「生菜是叶用变种，不等于莴苣的茎」）则在 `food_properties.json` 的 `note` 里留一句。
   *现状：`lianou` 有运行时 `note`，`shengcai`/`suan` 没有。*
2. **限定不得只在 JSON 里发光**：核验单 §4.4 增加一列（渲染 `how` 或 `mapping_review.note`），
   否则「限定」对唯一的读者（审核人）不可见。
3. **`layer` 与 `accepted` 的语义不要混**：`accepted` 说的是**映射**是否可用，不是**值**是否要改。
   现成的反例就是 `jiangyou`（映射可用、值不改）被写成 `group="…（**仍未采纳，待确认**）"`。

### 5.3 顺带修：核验单 §4.2 的「一律……加 `note` 留痕」与事实不符

### 5.4 顺带修：`outcome.rejected_detail` 的「28 → 27」

`sources.json` 写：
