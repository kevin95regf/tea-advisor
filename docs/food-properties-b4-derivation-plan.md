## 1. 待确定的清单（第一件要拍板的事）

### 1.1 三处分层口径打架（实测）

**证据一：`32` 是减出来的。** 上游 §0 写「能引来源 35 / 无来源 65」，§1 把 65 分成 L2 32 + L3 33。
但 `100 − 35 − 33 = 32` —— 32 是**余数**。而 33 也不实：§1.3 写「③-a **13** 条」，表内实列 **14 个名字**（苹果、柠檬、草莓、芒果、辣椒、酸奶、豆浆、面条（通称）、豆芽、可乐、奶茶、咖啡、啤酒、乌龙茶），另加「③-b **约** 20 条」。**两个数都是估的。**

### 1.4 由 §1.3 得出的三条判断

1. **L2 的真实规模 ≈ 47–55 条，不是 32 条。** 若坚持 32 条，就需要一条**更窄的准入**（例如「只做已有 `note` 的 16 + 上游点名的 16」），并把其余明确移入 L3 —— 这是**规模决定**，请你定（§9 拍板点 B）。
2. **7 条冲突全部落在两种形状**（这不是巧合）：
   - **「面食烤制」现值偏平**（吐司／蛋糕）：项目对烤面包类一律取平，规则会推温；
   - **「冰 + 另一正向因素」被规则抵平**（啤酒：发酵+1 与冰镇−1；去冰奶茶：回到平；凉茶：基底无条目）。
   ⇒ 这两族**恰好就是同学两条新规则要解决的问题**（加工深度分档、方向相反时不抵消）。**规则不是凭空加的，是有真实用例的。**
3. **2 条基底不可得**（咖啡／巧克力：**可可**在表和语料里都没有条目）⇒ 它们**天然不属 L2**，是 L3 的教科书样本。「基底不可得」是 R1 失效的判据。

## 2. 六条规则（逐条：内容 / 落点 / 张力）

### 2.1 R1 基底继承（**打补丁版**）

| | |
|---|---|
| **原规则** | 条目以某基础食材为主体时，取该食材四气（须写明基底名） |
| **补丁（同学）** | **加工方式可能改变基底的性味 ⇒ 不能直接取基底值**，须「基底 + 加工」联合定值 |
| **落点** | 每条 `note`（数据）＋ 规则成文 |
| **判据** | 基底必须在表内或已有登记；**基底不可得 ⇒ 本条退出 L2**（§1.3 的咖啡／巧克力）|
| **实测支持** | 57 条里 55 条基底可得；`kafei`／`qiaokeli` 不可得 |

**补丁的实质**：原规则「取该食材四气」暗含「基底值 = 成品值」，而 §1.3 里 **`youtiao`（面平→油条热）、`bingqilin`（乳平→寒）、`shujiaotiao`（土豆平→热）** 都是「未加工即基底值，加工后跨两档」的反例。
⇒ **R1 必须与 R2／R3 联用**，单独用会给出错值。这正是同学说的「不能只 ±1」。

### 2.2 R2 做法修正（**分层权重**）

| | |
|---|---|
| **原规则** | 油炸／烧烤／辛辣 → +1；生食／冰镇 → −1（复用 `nature_math` 常量）|
| **补丁（同学）** | ① **权重重定**：不能只 ±1；② **生食 −1 的权重高于冰镇 −1**；③ **腌制方向不确定时标「不确定」** |
| **落点** | `_meta.nature_change_rules`（**已有字段，已渲染进提示词**）＋ 每条 `note` |
| **⚠ 张力** | 落成「权重」则**必须动代码**（`COOKING_DELTA` 是 `int`），见 §3 |

**「生食 −1 权重高于冰镇 −1」怎么落地才不引入第四份词表**，三个选项：

| 选项 | 做法 | 后果 |
|---|---|---|
| **甲（建议）** | 只写**同现时的取舍规则**：两者同现时**取生食一项**（不叠加） | 零代码改动；解释力已够（寿司：米平 生食−1 = 凉 ✓）|
| 乙 | 生食记为 −2 | **改代码**（`raw: 0 → -2`）；`shousi`／`xila_suannai` 的既有裁定会被推翻（§3.4）|
| 丙 | 引入分数权重（生食 −1.0、冰镇 −0.5…）| **改代码 + 改数值轴语义**；`combine` 已支持 `float`，但 `apply_cooking_fallback` 返回 `int` 档 |

**实测：按甲，§1.3 里涉及生食的 3 条（寿司／沙拉／果汁…）全部自洽**，唯一不自洽的是 `shengyu`（生鱼片，现值 `cold`）。⇒ **甲能覆盖 47/47 的一致项**，不需要乙。故建议甲。

### 2.3 R3 加工深度（**新增维度**）

| | |
|---|---|
| **内容（同学）** | 轻度／中度／深度加工，**偏移不同档位** |
| **落点** | 规则成文 ＋ 每条 `note` 写明档位 |
| **为什么必须有** | 它能解释**原规则解释不了的 4 条**：`youtiao` 热、`shujiaotiao` 热、`bingqilin` 寒、`zhayu_shutiao` 热 —— 这 4 条都需**在做法之外再加一档** |

**建议档位表（草案）**：

| 档位 | 判据 | 增量 |
|---|---|---|
| 轻度 | 单次加热／烤／煮，未见「双重/深度/久」 | +0 |
| 中度 | 常规油炸／炒／烤 | +1 |
| 深度 | 明写「双重／深度／久炖／重油」或**跨两档的成品** | +2 |

⚠️ **`tusi`／`dangao` 的冲突正好卡在「轻度 vs 中度」的界上**：若判吐司的「烤」为**轻度（+0）**，两条冲突**立刻消失**。⇒ 档位表不只是新规则，它同时是**消解冲突的杠杆**（§9 拍板点 C）。

### 2.4 R4 发酵（**新增维度**）

| | |
|---|---|
| **内容（同学）** | 酒／曲类 +1；**乳发酵 0**；**不确定则标注** |
| **落点** | 规则成文 ＋ `note` |
| **实测支持** | ① `pijiu`（啤酒）：酒曲发酵 +1 与冰镇 −1 **互相抵消** ⇒ 正好触发 R6；② `puerg`（熟普，后发酵）+1 → 温 ✓；③ `naicha`／`naixicha`／`xila_suannai`（乳发酵）取 0 ✓ |
| **⚠ 张力** | 「乳发酵 0」与 `xila_suannai` 的既有 `review_note`（去掉 cold 变体）方向**一致** ✓ —— 这条无冲突 |

### 2.5 R5 多成分合成（**保留 + 一处判据要改**）

| | |
|---|---|
| **原规则** | 主体成分为主，辅料只作 ±1 内的微调；**不做跨档跳跃** |
| **落点** | 规则成文（引用 `nature_math.combine` 的现成实现）|
| **实测支持** | `sanmingzhi`／`sanmingzhi_huotui`／`hanbao`／`niurou_hanbao`／`pisa` 全靠「**辅料不跨档**」才与现值一致 |
| **⚠ 张力（重要）** | `combine()` 的判据是「**取绝对值最大者为主导项**」；而 L2 的实际口径需要「**主体＝占比最大的主食基底**」。**两者在汉堡／寿司／三明治上给出不同答案** |

**举例（同一输入，两种判据两种答案）**：

- `niurou_hanbao`：面包(平) + 牛肉(温) + 煎烤(+1)
  - 按 `combine` 的「绝对值最大」→ 牛肉为主导 → 温+1 再 +烤 = **热** ✗
  - 按「主体=面包」→ 平+烤 = **温** ✓（与现值一致）

⇒ **建议 R5 采用「主体＝主食基底」**，并在文档里写明这与 `combine()` 现有判据的差别（`combine` 未接入主流程，见 §3.1）。

### 2.6 R6 冲突标记 ＋「不确定」包装

## 5. 数据层改动（`note`）与两条硬约束

### 5.1 `note` 是运行时字段（**实测**）

`note` 会被 `resolve_temperature_fields(name, note)` 扫描，命中温度词即给四气 **±1**。
**实测条件比文档更窄、也比文档更宽**：

- **窄**：只在 `len(note.replace(" ","")) <= 10`（`NOTE_MAX_LEN`）时才扫；
- **宽**：「备注通道」的锚定判据是 **`_find_entry(剥掉温度词后的余文)` 非空** —— 而 `_find_entry` 第 1 级是**包含匹配**，所以**余文里含任意条目名即可通过**（不必「恰好等于」条目名）。

**实测全表**（147 条，38 条有 `note`）：**4 条**会让 `resolve_temperature_fields` 返回信号。

| id | `note` | 长度 | 命中 | 通道 | 备注 |
|---|---|---|---|---|---|
| `suannai_wan` | 冷藏酸奶加水果，偏凉 | 10 | −1 | **`note`** | 余文含「酸奶」→ 通过包含匹配 |
| `bing_naicha` | 奶茶为平，冰镇后偏凉 | 10 | −1 | `name`（「冰奶茶」的「冰」）| — |
| `qubing_naicha` | 去掉冰后仍比热饮偏凉，故记为凉 | 10 | −1 | `name`（「去冰」）| — |
| `re_naicha` | 奶茶为平，加热后偏温 | 10 | +1 | `name`（「热」）| — |

⚠️ **现有守卫只守了 `jiangyou` 一条**（`test_jiangyou_note_has_no_temperature_side_effect`）。
⇒ **B4 要批量写 32（或 47）条 `note`，等于有 32 次踩雷机会，而防线只有 1 条。**

### 5.2 `note` 的三条硬约束（写作纪律）

1. **不得出现温度前缀词**：`冰镇/冰/加冰/去冰/冷冻/冷藏/冻`、`热/烫/加热/温热`。
   ⚠️ 「**温**」单字安全（不在前缀表），但「**温热**」**不安全**；「冰」字**只要出现**就可能命中。
2. **长度**：建议统一 **> 10 字**（最省事的兜底），或确保 ≤10 字时**不以温度词开头/不含温度词**。
3. **不得与现值矛盾**：推得值必须写在 note 里并与 `nature` 一致；不一致的走 §2.6（R6）登记为冲突。

**建议的 `note` 模板**（与现有 16 条风格一致、且可复核）：

```
基底 <基底名>（<四气>） + <加工>（<增量>） = <成品四气>[；档位 <轻/中/深>][；配料 <配料>（<增量>）]
```

示例（改写现有两条以示范）：
- `youtiao`：`基底 面（平） + 深度油炸（+2） = 热；档位 深`
- `shousi`：`基底 米（平） + 生食（−1） = 凉；配料 醋（调味，不抵消）`

### 5.3 必须新增的守卫（把「1 条」扩到「全表」）

`remaining-plan` §6 已提过「守卫③」，B4 要真的做出来：

| 守卫 | 内容 | 为什么不能只守一条 |
|---|---|---|
| **① 全表 note 无温度副作用** | **遍历 147 条**，断言 `resolve_temperature_fields(name, note) is None`；**含负控制**（喂一条 `note="冰镇奶茶"` 的合成条目，必须变红）| 把 `jiangyou` 的单条守卫升级为**派生不变式**；否则每写一条 note 都是一次静默改值的风险 |
| **② 一致项必须自洽** | 断言「`note` 里写出的基底＋增量」推得值与 `nature` 相等（**只对声明了派生 note 的条目**）| 防「note 说得通、值却是另一个」|
