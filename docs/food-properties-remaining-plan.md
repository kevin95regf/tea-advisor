## 3. 无来源的 65 条，怎么处理

### 3.1 L2 派生层（32 条）—— 建立派生规则，不是编来源

**目标**：让每条的 `note` 能回答"这个值是怎么来的"，且**可复核、可反驳**。

**要成文的三条规则**（从现有 note 抽出来，不新发明）：

1. **基底继承**：条目以某基础食材为主体时，取该食材四气（须在 note 写明基底名）
2. **做法修正**：油炸／烧烤／辛辣 → +1；生食／冰镇 → −1（**复用 `nature_math` 现成常量**）
3. **多成分合成**：主体成分为主，辅料只作 ±1 内的微调；**不做跨档跳跃**

**写法模板**（沿用现有 note 风格）：

```
基底 X（平） + 做法 Y（+1） = 温
```

**验收标准**：任何人照 note 能推出同一个值。推不出来 = 不合格。

### 3.2 L3 无据层（33 条）—— 标 ③ 显式留痕

按 `batch2-plan.md` §2.1 的层③定义：

> 标 `null` + 「无权威来源，凭专业判断」—— **不得用通行表述伪装权威依据**

落到登记表的字段：

| 字段 | 值 |
|---|---|
| `evidence` | `[]`（空） |
| `status` | `无源可引` |
| `layer` | `③` |
| `open_question` | 写明「50 号文件 §5.2 真无据」或「结构性无据：现代／外来／工业品」 |

**关键区分**：③ 层**不是数据错**，不要顺手改值。项目现值来自专业判断，保留；只是**不宣称它有来源**。

> 这一层有个容易被忽略的正面意义：它的存在本身就是诚实性的证据 ——
> 一个 147 条全都有"古籍依据"的表，反而更可疑。

## 5. 三个必须先拍板的问题

### 拍板点 1：茶饮 11 条，认不认「继承原料四气」？

| 选项 | 后果 |
|---|---|
| **甲：认**（建议） | 11 条升为 L1，登记为「制品·原料继承」，须在 `evidence` 注明"制品，依 §5.2 本无条目，此处按原料四气取值" |
| 乙：不认 | 11 条降为 L3，与乌龙茶／普洱同列无据；项目茶饮场景的四气**全部退回模型推测（置信 0.3）** |

**建议甲**，理由三条：

1. 项目是**茶饮推荐工具**，茶饮四气是核心命脉；退成无据等于把最要紧的场景交给模型猜，违反项目原则（判断权在表和规则）。
2. 这 11 味的原料是**药食同源饮片**，`herb_nature_reference.json` 有药典对照，比"绿茶 S1:566 方向性描述"更硬。
3. §5.2 那条原则针对的是「**本库无条目就别装作有**」，而我们可以**显式标注这是继承**——标了就不算伪装。

**但这条必须由你定**，它改变的是数据口径，不是执行细节。

### 拍板点 2：面制品 5 条（馒头／面条／饺子／包子／小笼包）判平还是判温？

项目现值是 `neutral`，语料 §4.2「面（面粉）**温**」纲目 18855。
而 §5.2 又单独把「面条」列为真无据 —— **同一条在两个章节出现，须择一**。

**建议**：维持 `neutral`，登记为「口径分歧」，理由同第一批的白菜／黄瓜／莲藕（教材 vs 纲目，无权威裁定前不动值）。但**要在 `open_question` 写清两处来源**。

### 拍板点 3：派生规则的产出落在哪？

| 选项 | 说明 |
|---|---|
| **甲：写进 `food_properties.json` 的 `note`**（建议） | 用户可见，且 `note` 会被渲染进提示词 |
| 乙：写进 `sources.json` 的独立字段 | 不污染数据表，但用户和模型都看不到 |

⚠️ **选甲有个坑**：`resolve_temperature_fields(name, note)` **会同时扫 name 与 note**，命中 `CHILL_PREFIXES`（冰镇/冰/冷冻/冷藏…）或 `HEAT_PREFIXES`（热/烫/加热/**温热**）就给四气 ±1。
