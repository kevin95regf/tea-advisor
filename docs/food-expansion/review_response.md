## Q1　先确认分类标准：WS/T 464 是不是要的？

### 1.1 核实结果（2026-10-08 联网核实）

| 标准 / 资料 | 性质 | 发布 / 编者 | 现状 | 分类方式 | 适不适合本项目 |
|---|---|---|---|---|---|
| **WS/T 464-2015《食物成分数据表达规范》** | 卫生行业标准，**推荐性**，营养学（食物成分数据） | 国家卫生计生委，2015-04-28 发布，2015-11-01 实施；起草单位为中国疾控中心营养与健康所（杨月欣等），另有上海、浙江疾控 | 全国标准信息公共服务平台显示**现行**（页面时间轴上有一个"废止"字样，是没有日期的通用标签，不是状态）。没查到修订稿或征求意见稿 | 表 1 列 20 类，"类-亚类-小类"三级，**按原料属性**分；官方解读说也参考了 GB 2760 / GB 14880 的加工食品分类 | ✅ 适合当存储层细分类 |
| 《中国食物成分表》标准版第 6 版（杨月欣主编，北大医学出版社，第一册 2018 / 第二册 2019） | 营养学数据书 | 中国疾控中心营养与健康所 | 现行最新版 | 和 WS/T 464 的结构相同（类-亚类-小类 + 顺序码 + 附加码），但书里**有部分类号沿用 2009 版的 21 类编号**（例如第二册里的动物油脂、"其他"） | ⚠️ 只能当交叉参照。逐条食物码需要书本原文，我们核实不了，所以不采用 |
| **《中国居民膳食指南（2022）》/ 平衡膳食宝塔（2022）** | 营养学膳食指导 | 中国营养学会 | 现行。第 5 次修订 2026 年已经启动（6 月上海会议、9 月科学会议），**截至 2026-10-08 还没出新版** | 5 层：谷薯类 / 蔬菜水果 / 鱼禽肉蛋等动物性食物 / 奶类、大豆和坚果 / 烹调油和盐；酒和添加糖"不是膳食组成的基本食物" | ✅ 适合当用户可见的粗分类 |
| GB 2760 食品分类系统 | **食品添加剂使用法规** | 国家卫健委 / 市场监管总局 | — | 按添加剂管理需要分 | ❌ 不是营养学分类，不用 |
| NY/T 3944-2021 食用农产品营养成分数据表达规范 | 农业行业标准 | 农业农村部 | — | 只管农产品 | 和本项目范围不符，只作附注 |

所以 WS/T 464 回答得了"是不是营养学标准"：**是**，而且是国内食物成分领域最直接的一部。但它的用途是**统一食物成分数据怎么表达、怎么交换**，粒度很细（例如 04-7 薯芋类），不是给用户看的膳食分组。用户能看懂的营养学口径是膳食指南宝塔。

### 1.2 仓库里 `category` / 分类现在拿来干什么（代码证据）

- `core/data/food_properties.json` 的 `_meta.field_notes.category`：「分类，便于按类兜底判断」。
- **运行时唯一消费者**是 `core/app/domain/diet_signals.py`：
  - `_food_index()`（172–195）按名称或别名找到条目，读 `category`；
  - `identify_signals()` 用 `category` 判断 `alcohol`（`酒类`）、`high_sugar`（`甜点` / `冷饮` / `甜汤`）、`dairy`（`乳饮`）（322、336–341），`_is_spicy()` 遇到 `酒类` 直接否决（261–282）。
  - 类目名单在 `core/data/diet_signals.json` 的 `signals[].rule.categories`。
- 其余引用都在脚本或文档：`core/scripts/build_food_review_sheet.py`（核验单按类排版、检查缺 category）、`docs/pending-items.md` D23 第 550 行（「`category` 已填 129/147，`乳饮`/`甜点`/`冷饮`/`甜汤`/`酒类`/`饮料` 正好被单独分出」）。
- 仓库文档里**没有任何地方**要求营养学分类（全仓搜"膳食 / 营养 / 食物成分 / WS/T"，只在引用《中医饮食营养学》时出现）。所以营养学分类是**新增用途**（数据治理、审核、以后做膳食结构分析）。现有代码不需要它，它也**不能替代 `category`**：信号判定靠的是 `酒类` / `甜点` / `乳饮` 这些项目自己定的口径，例如 WS/T 464 里没有"甜点""冷饮"可以直接对应高糖信号的小类。

### 1.4 已发现、需要更正的宝塔层错标（依据：宝塔 2022 解析原文，dg.cnsoc.org）

原文要点：「杂豆包括大豆以外的其他干豆类，如红小豆、绿豆、芸豆等……把杂豆与全谷物归为一类」（第一层）；「蔬菜包括……鲜豆类……菌藻类及水生蔬菜类」（第二层）；第四层是「奶类、大豆和坚果」；「大豆包括黄豆、黑豆、青豆」。

| 问题 | 条目 | 现标签 | 应为 |
|---|---|---|---|
| 杂豆误归大豆 | 红豆、芸豆、蚕豆、鹰嘴豆、豌豆（5 条，都是新增） | 大豆和坚果类（大豆及制品） | **第一层 谷薯类（全谷物和杂豆）**；黑豆仍属大豆 |
| 奶类层号 | 牛奶、酸奶、希腊酸奶、酸奶碗、羊奶（5 条） | 畜禽鱼蛋奶类（奶类） | 标签取自原文"5 大类"的说法，可以保留，但**分层属第四层** |
| 菌藻说明 | 海带、紫菜、蘑菇、香菇、木耳、银耳、石花菜（7 条） | "指南是否计入蔬菜本次未核原文" | 原文已确认**计入蔬菜**（第二层），把这句说明删掉 |

这三处**已经体现在** `split/` 的 `dg2022_layer` 和 `dg2022_layer_note` 里。原始的 `dietary_guidelines_2022` 文本按"不改既有值"的原则保留原样，等审核人确认后再统一改。

### 1.5 建议与下一步
1. 所有者确认采用 **A**（WS/T 464 存储 + 宝塔展示），并确认**不用分类替代 `category`**。
2. 如果选 B，需要改：删掉 7 个 `food_group_*` 字段以及 `classification_status` / `classification_source` / `classification_note`；`food_classification.csv` 改列；README §2–4、§6 重写。`split/` 的运行时表只需要去掉 `food_group_code`。
3. 不管选哪个，分类字段**都不进 `note`**（`note` 会被 `food_lookup` 扫温度前缀，也会被 `render_reference` 写进提示词）。

### 4.2 食物是"输入信号"，饮片是"输出推荐"，代码里怎么分的
- **食物表只往前走**：它只喂 `calibrate_parsed`、`resolve_in_context` → `ParsedFood.nature/flavors` → `identify_signals` / `detect_nature_conflict` → plan 触发和场景规则。`core/app` 里**没有任何地方**把食物条目放进候选集或推荐结果。
- **饮片表只往后走**：候选集是 `filter_by_constitution`（`safety.py:482`），推荐和护栏用 `herb_by_name`（`safety.py:154`），全部只读 `herbs.json`。
- 两边**没有共享 id，也没有交叉引用**。同一种东西在两边各有一份取值（桑椹就是凉 vs 寒）。

### 4.3 "吃了山药又被推荐山药"，代码怎么处理
实测（LLM 路径模拟，特禀质，口述"山药炖排骨，饭后吃了冰西瓜和烤羊肉"）：冰西瓜（寒）和烤羊肉（热）形成寒热错杂，L1 退到体质默认方，推荐「**山药红枣平补饮**（山药 10g、红枣）」。**原表和扩充表下结果一样**，唯一的差别是食物"山药"的来源从 llm 0.3 变成 rule 0.9。所以：
- 现在**没有去重或提示**：`fallback_recommend` 的硬剔除只看 `exclude_herbs` 和体质的 `unsuitable_for`（`matcher.py:510–555`），Agent2 提示词里虽然有 parsed foods，但没有任何约束说"不要重复"。
- 用量上也**不累加**：`max_daily_g`（山药 20g）只管茶方本身，不算餐里吃了多少。
- 这和项目定位一致（「事后处理」：吃了什么 → 喝点什么，见 pending-items D20/D22 的裁定），**本身不算 bug**，但需要所有者表态。可选做法：保持现状；或者只在 `cautions` 里加一句提示；**不建议**从候选集里剔除，因为会改变方向收敛，而且和"不做拦截"的裁定冲突。

### 4.4 仓库已有的先例
- **昆布 / 海带（E8，`docs/pending-items.md:781–792`）**：食物表 `haili` 的别名里有"昆布"，饮片扩充时因此暂缓了"昆布"（`docs/herbs-expansion-11-plan.md:52`）。E8 列了三个选项：**(α)** 不立饮片条目；**(β)** 两处并存、互相标注（写明以谁为准、另一处为什么保留）；**(γ)** 删掉食物表别名后再立饮片条目（`aliases` 和 `keywords` 两处都要清），目前**待所有者确认**。

### 4.5 选项与建议

| 选项 | 内容 | 评价 |

| ① 共享 id 交叉引用 | 在**分类侧车**（不是运行时表）里给 4 条新增和 13 条原有重叠加 `herb_id`（如 `yimi → yiyiren`），并写明"食材（鲜品 / 日常食用） vs 饮片（干品 / 药典）"的口径差 | ✅ 推荐，等于 E8 的 (β)；不动运行时，不影响测试 |

### 5.4 校验结果
1. **无损**：运行时表 + 两个侧车按 id 合并后，226 条和 `food_properties_expanded.json` **逐条完全相等**（`dg2022_layer` 是新增派生字段，比对时去掉）。
2. **原 147 条不动**：在运行时表里，15 个字段的值和键序与仓库原表**逐条相等**。
3. **加载器兼容**：换进仓库副本后，`table_stats()` = 208 + 18 = 226；38 个离线口述 × 9 体质、15 个 LLM 路径模拟、76 个探针名的结果和扩充全字段表**完全相同**（JSON 级比对 `True`）。
4. **测试**：运行时表 226 条 → 832 过 / 9 失败，和扩充全字段表相同，即 5 个计数钉死 + 4 个环境性失败；只加分类的 147 条版本 → **837 过 / 4 失败，和基线相同**。

### 5.5 对测试和文档的影响
- `docs/data-contracts.md:15` 写的是「字段集合＝`FIELD_ORDER`（15 个）」，`test_doc_declares_actual_field_order_length` 会核对 `FIELD_ORDER` 的长度和文档是否一致。如果运行时要带那 2 个分类字段，按规矩应该加进 `patch_food_table.py:49` 的 `FIELD_ORDER`（变成 17），并同步文档。**如果连这 2 个字段也不想进运行时**，就把它们也放进分类侧车，运行时表回到纯 15 字段（226 条约 112 KB，147 条和原表字节相同）。两种都可以，看所有者是否想让运行时"看得见"分类。
- **证据侧车最终放哪**：仓库已经有一个证据登记表 `docs/food-properties-sources.json`（`{_meta, entries[94]}`，每条 `evidence[]` 的字段是 `source_id / tier / matched_name / how / locator / verbatim / qi_word / qi_mapped`，和我们的 `tcm_evidence` 基本同构），**只有 `build_food_review_sheet.py` 和测试读它，运行时不读**（`docs/data-contracts.md`：「`docs/*.json` 不被运行时读」）。而且 `test_remaining_plan_facts` 要求"全表条数 = 已登记 + B4 派生"。所以**建议**：新增条目的证据**转写进这个登记表**（多出来的 `url / verification / origin` 作为扩展键），不要在 `core/data/` 另立证据文件；分类侧车可以放在 `docs/`（例如 `docs/food-classification.json`）。这样 `core/data/` 只放运行时数据。
