## 1. 六条规则（成文）

### R1 基底继承（打补丁版）

条目以某基础食材为主体时，**不能直接取该食材四气** —— 加工会改变基底的性味，须「基底 + 加工」联合定值。

- **判据**：基底必须在**表内**（或有已登记的四气）。基底不可得 ⇒ 本条**退出 L2**。
- 反例（说明补丁为什么必要）：`youtiao`（面平 → 成品热）、`shujiaotiao`（土豆平 → 热）、`bingqilin`（牛乳平 → 寒）—— 都是「未加工即基底值，加工后跨两档」。
- **复合主体**：主体不是单一食材的（火锅、咖喱、麻辣香锅、沙拉、果汁），基底记 **「复合（平起算）」**，不得拿「蔬菜」「水果」这类**表内不存在的类目**顶。

### R2 做法修正（方向性 ±1）

| 做法 | 增量 | 说明 |
|---|---|---|
| 生食 | **-1** | 甲案：与「冷藏/冰镇」**同现时只计一次**（取生食），不叠加、不引入 -2 |
| 冷藏/冰镇 | **-1** | 属 R3 的「轻·冷向」档 |
| 辛辣/重辣 | **+1** | |
| 热汤/烫煮 | **+1** | |
| 腌制 | **0** | **方向不确定**：不硬判，按 R6 在 `note` 里标「方向不定」 |

### R3 加工深度（档位登记表）

**同一加热强度分档，档位由做法本身决定，不得拿数据现值倒推**：

| 档 | 增量 | 做法 |
|---|---|---|
| **轻** | **+0** | 煮（蒸、卤、焯）；**定型烘焙**（吐司、蛋糕 —— 面点定型，含水高） |
| **中** | **+1** | 炒；明火烧烤；**高温/脱水烘烤**（披萨、饼干）；油糖酱焖烧（红烧）；久煮焖烧（火锅、麻辣香锅、咖喱）；卤汁浓酱 |
| **深** | **+2** | **油炸**（单次与双重同判）；**深度冷冻**（冷向 -2） |
| 轻·冷向 | -1 | 冷藏、冰镇 |
| 深·冷向 | -2 | 深度冷冻（冰淇淋） |

**「油炸为什么整档记深」的依据**（数据驱动，非口味判断）：表内 5 条油炸成品 **5/5** 相对基底跨两档 —— 面平→油条热、土豆平→薯条热、鱼平→炸鱼薯条热、鸡温→炸鸡热（夹取后仍为热）。单次与双次同判，故「双重油炸」不再额外叠档。

**本批 3 处档位判断（写在这里是为了被审，不是为了凑现值）**：

| 条目 | 本批判 | 备选 | 若判备选会怎样 |
|---|---|---|---|
| `pisa`、`binggan` | 高温/脱水烘烤 → **中 +1** | 与吐司同判「定型烘焙」轻 +0 | 两条立刻变**冲突**（推平 vs 现值温） |
| `hongshao` | 油糖酱焖烧 → **中 +1** | 「重油浓酱」判深 +2 | 立刻变**冲突**（推热 vs 现值温） |
| 沙拉、果汁 | 复合（平起算）＋生食 -1 → 凉 | 拿「蔬菜」「水果」类目当基底 | 违反 R1 判据（类目不在表内） |

### R4 发酵（新增维度）

| 情形 | 增量 |
|---|---|
| 酒／曲类发酵（啤酒、熟普后发酵） | **+1** |
| 乳发酵（奶茶、奶盖、酸奶） | **0** |
| 半发酵（乌龙茶） | **0** |
| 不确定 | 不硬判，按 R6 标「不确定」 |

### R5 多成分合成

主体成分为主，辅料只作 **±1 以内微调、不跨档**。

- **判据（本批修正）**：主体 = **占比最大的主食基底**，**不是** `combine()` 现用的「绝对值最大者」。
  - `niurou_hanbao`：按 `combine` 的「绝对值最大」→ 牛肉主导 → 温+烤 = **热**（✗）；按「主体=面包」→ 平+烤 = **温**（✓ 与现值一致）。
- 辅料不贡献增量时，`note` 记「配料 X（不跨档）」；**贡献增量时显式入算式**（`chadan`：配料茶叶（红茶温）+1）。

### R6 冲突标记与「不确定」包装

| 情形 | 处置 |
|---|---|
| 修正方向相反（啤酒：酒曲 +1 与冰镇 -1） | **不抵消**，标「属性冲突」，值不动，登记待裁定 |
| 依据不足（去冰奶茶、凉茶、生鱼片） | 给**倾向性判断 + 依据 + 建议**，值不动，登记待裁定 |
| 方向不确定（腌制） | `note` 里写「方向不定」，不硬判 |

**硬约束**：冲突条的 `note` **不得伪装成自洽**（不许写成「…所以是凉」）。必须出现「属性冲突」「项目值记 X」「待裁定」三要素 —— 这也正是守卫 ③ 的断言对象（§7）。

## 2. `note` 写作纪律（运行时硬约束）

`note` **不是注释，是运行时字段**：`resolve_temperature_fields(name, note)` 会扫它，命中温度词即给四气 ±1。实测条件（比函数注释更窄也更宽）：

- **窄**：只在 `len(note.replace(" ", "")) <= 10`（`NOTE_MAX_LEN`）时才扫 `note`；
- **宽**：`note` 通道的锚定判据是 `_find_entry(剥掉温度词后的余文)` 非空，而 `_find_entry` 第 1 级是**包含匹配** ⇒ 余文含任意条目名即可通过。

**B4 的两条纪律**：

1. **长度 ≥ 18 字（去空格）** —— 拟写的 53 条 `note` 实测最短 18 字，全部越过 `NOTE_MAX_LEN` ⇒ `note` 通道对它们恒不生效。
2. **不得写「冰镇/冰/加冰/去冰/冷冻/冷藏/冻」「热/烫/加热/温热」等前缀词** 作为可命中的短描述（长文案虽安全，仍避免把这些词当短语开头单列）。

### 顺带修好的一处既有副作用（实测）

`suannai_wan` 现有 `note`「冷藏酸奶加水果，偏凉」（去空格 10 字）**正好卡在上限**，于是：

| | 走哪条路 | 结果 |
|---|---|---|
| 不带 `note` | 查表直取 `酸奶碗` | 凉，置信度 **0.9**，detail「酸奶碗」 |
| 带现有 `note` | `note` 通道剥出「酸奶加水果，偏凉」→ 包含匹配命中 **`酸奶`** | 仍是凉，但置信度掉到 **0.6**，detail 变成「酸奶」 |

**四气没变，置信度与依据文案变了** —— 两个都是用户可见字段（`verification.detail` 用户可见）。B4 把这条 `note` 改成长文案后，`note` 通道不再触发，**该条回到 0.9 直取**。这是 B4 的一项实际收益，由守卫 ① 锁死。
