## 1　缺口 1：`agent2_system.md` 补齐 4 型

### 1.1　现状取证

`core/app/agents/prompts/agent2_system.md:41-46`：

```
2. **再对齐体质方向**：
   - 平和质：随餐调整即可，不必刻意
   - 气虚质：健脾益气方向，避免寒凉
   - 阳虚质：温性为主，避开寒凉饮片
   - 痰湿质：健脾利湿方向，避开甜腻补品
   - 湿热质：清热利湿方向，避开温燥补品
```

而 `core/data/constitution.json` 有 **9 型**，全部可对外（闸门 `ready_constitutions()` 已放行 9 型）。

**已排除的范围**：全仓 grep `阴虚质：` / `痰湿质：` / `健脾益气方向` 等特征串，
命中只有 `agent2_system.md` 这一处（其余命中在 `dsh-home/` 会话缓存里，非源码）。
**所以「4 行」就是全部改动，没有第二份需要同步的表。**

### 1.2　一个必须先讲清的结构事实

`agent2_recommend.build_user_prompt()` 已经把**该体质的《饮食原则》与《应避免》注入用户提示词**，
数据直接读自 `constitution.json`（9 型全有）。也就是说：

> `agent2_system.md` 里这份 9 型方向清单，**是 `constitution.json` 的第二份副本**。

所以本次不是「新增 4 条知识」，而是「把已经存在于唯一真源里的 4 型，在提示词副本里补上」。
补完之后仍存在两份，**因此第 1.4 节必须加一条防漂移守卫**，否则下次加体质还会漏。

### 1.3　改动内容（确切文字）

在第 46 行「湿热质」之后按 `constitution.json` 的 id 顺序追加 4 行，
措辞对齐既有 5 行的简省风格（括号细节仍只存在于 `constitution.json`）：

```

   - 血瘀质：行气活血方向，少用涩滞收敛之物
   - 气郁质：理气解郁方向，避开酸涩收敛之物
   - 特禀质：平补固表方向，避开发物与个体已知过敏原
```

**逐行溯源**（写的不是对方的措辞，是 `constitution.json` 自己的措辞）：

### 1.4　防漂移守卫（本项目测试范式的标准做法）

新增 `core/tests/test_agent2_prompt.py`：

1. **派生不变式** `test_agent2_prompt_covers_all_constitutions`
   从 `data/constitution.json` 读出全部 id→label，断言**每个 label 都出现在 `agent2_system.md` 里**。
   不写死「9」或「4」—— 下次加第 10 型，这条自动变红，**强制做一次显式决定**（正是这个测试的目的）。
2. **负控制** `test_coverage_check_negative_control`
   把判定抽成纯函数 `_missing_constitution_labels(prompt_text, constitutions)`，
   喂一份**人造的**第 10 型（如 `blood_deficiency 血虚质`），断言它被报出来。
   没有这一步，「真实数据上没报错」和「检查根本没跑」长得一模一样。
3. **守卫范围限定**：只查 §推荐逻辑 里那 9 行方向提要（按 `- 　质：` 行首匹配），
   不查全文 —— 否则示例段里出现「痰湿质」会把测试变成假的通过条件。

### 1.5　不采用的方案

| 方案 | 为何不采用 |
|---|---|
| 从 `constitution.json` 渲染 §推荐逻辑 | `agent2_system.md` 是静态文件，由 `load_system_prompt()` 直读；要渲染就得引入模板引擎或运行期拼接，改动面远大于收益 |
| 删掉 §推荐逻辑 那 9 行，只靠用户提示词里的《原则/应避免》 | 这 9 行还有「一句话方向词」的收敛作用（模型快速定位方向），删掉后需重新验证推荐质量，风险大于收益 |
| 照抄对方那 4 行文字 | 血瘀质一行的语义与本项目数据不一致（见 1.3） |

### 2.3　影响面（全部实测，不是推断）

**必须煎煮味在各体质候选池中的位置**（下标 0 = 首位，直接进提示词首行）：

| 体质 | 命中 | 最高位 |
|---|---|---|
| 平和质 | 茯苓 | **茯苓@0** |
| 气虚质 | 茯苓、莲子、山药、白扁豆 | **茯苓@0** |
| 痰湿质 | 茯苓、薏苡仁、白扁豆 | **茯苓@0** |
| 特禀质 | 山药、茯苓 | **山药@1**、茯苓@2 |
| 阳虚质 | 茯苓、莲子 | 茯苓@5 |
| 阴虚质 | 百合、莲子 | 百合@10 |
| 湿热质 | 百合、薏苡仁 | 百合@6 |
| 血瘀质 / 气郁质 | 茯苓 | 茯苓@3 |

**9 个体制的 top12 候选，每一个都含至少 1 味必须煎煮的** —— 也就是说，**LLM 路径几乎必然遇到这个问题**，
而 `茯苓` 在 3 个体质里排在**候选清单第 1 行**，被选中的概率最高。

**兜底路径上会切换冲泡方式的搭配**：

| 位置 | 搭配 | 命中 |
|---|---|---|
| `CONSTITUTION_DEFAULT` 痰湿质 | 茯苓 8g ＋ 陈皮 5g（茯苓陈皮化湿饮） | 茯苓 |
| `CONSTITUTION_DEFAULT` 特禀质 | 山药 10g ＋ 红枣 8g（山药红枣平补饮） | 山药 |
| `RULES.sweet_heavy` | 茯苓 6g ＋ 陈皮 4g | 茯苓 |
| `RULES.late_night` | 陈皮 4g ＋ 茯苓 6g | 茯苓 |

其余 7 型默认搭配、另 1 条规则搭配**不含**必须煎煮味 → 行为不变。

**⚠️ 这是本方案唯一会被用户直接察觉的行为变化：痰湿质与特禀质的默认搭配，
会从「保温杯焖 6–8 分钟」变成「养生壶煮 20–30 分钟」。** 见 2.4 的三个方案。

**用量上限**（写 `COOK_BREW` 的 `steps` 时要对齐）：茯苓/百合/莲子 15g，薏苡仁/山药/白扁豆 20g。

### 2.4　三个方案（**这一步需要你选**）

| | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A** 引入煎煮路径 | 保留默认搭配，含必须煎煮味时切到 `COOK_BREW` | 诚实，荐的是真能出味的喝法 | 用户被要求有养生壶/小锅；痰湿、特禀两型默认搭配的体验变了 |
| **B** 默认搭配避开必须煎煮味 | 把痰湿默认的茯苓换成不必煎煮的同类（如荷叶/薏苡仁→陈皮＋荷叶），必须煎煮味只在候选清单里保留并标记 | 主路径仍是「保温杯」这一套，体验一致 | 等于承认「这个产品给不出茯苓」，而茯苓是候选首位，回避得了一处回避不了全部 |
| **C（推荐）** A ＋ B 一起 | 默认搭配尽量避开；一旦真用到（模型自选或兜底命中），就走煎煮路径并明确写清 | 主路径体验不变，又不撒谎、也不挡路 | 实现量略大：要多定一条「默认搭配选择纪律」 |

**推荐 C 的理由**：B 单独用会留下漏洞 —— 模型是自由选料的，它照样可能挑茯苓（茯苓在 3 个体质里排第 1 位），
只字未提煎煮照样给出「保温杯焖 8 分钟」。C 把「默认路径避开」与「真用到时讲清楚」都做了，两个问题各自闭合。

### 2.5　四层落地设计（以方案 C 为准）

#### 第 1 层 · 数据：给 6 味加结构化标记

在 `core/data/herbs.json` 这 6 味的 `brewing` 对象里，**统一作为最后一个键**追加：

```json
"brewing": {
  "form": "切块或薄片，质地坚实",
  "note": "需先煎或久煮 10 分钟以上才易出味，直接冲泡效果差",
  "prep": "可先用温水浸泡 10 分钟再煮",
  "requires_cooking": true
}
```

- **为什么进数据、不在代码里写常量**：对方就是把 5 个名字硬编码进 `matcher.py`。
  一旦数据侧改了判定（比如补了「百合」），常量不会跟着变 —— 两份名单必然漂移。
  标记与它的理由（`note` 原文）放在同一个对象里，改的时候看得见依据。这也与 `unsuitable_for` 的处理方式一致。
- **为什么不是新造顶层字段**：`brewing` 已是自由 dict（`models.py:235` `dict[str, Any]`），
  加子键不触碰任何 schema；`_meta.field_notes.brewing` 顺手补一句子键说明即可。
- **写法**：`herbs.json` 是内联数组格式，**只能文本级精确替换**（项目既定姿势，不能用 `json.load`+`dump` 回写）。
- **版本**：`_meta.version` `0.4.0` → `0.5.0`（与上次数据改动同一习惯）。**这一条要你点头。**
- 已实测：**没有任何测试或脚本校验 `brewing` 的子键**（全仓 grep `brewing` 只命中 `herbs.json` 自身与 `models.py:235`），
  所以加子键不会撞守卫。

#### 第 2 层 · 提示词：让模型看得见

**(a) 候选清单行**（`_candidate_lines()`）—— 只在有标记时追加，**未标记的 28 味渲染字节不变**（提示词 diff 最小）：

```
- 茯苓（平，甘/淡，归心/肺/脾/肾）｜功效方向：利水渗湿、健脾｜单日上限：15g｜⚠️ 须煎煮，不可只冲泡
```

**(b) 系统提示词**新增第 6 条推荐逻辑（约 10 行）：

```
6. **冲泡方式要跟着饮片走**：
   - 候选清单里标了「⚠️ 须煎煮」的，不能用保温杯焖泡：`vessel` 写「养生壶」或「小锅」，
     `water_temp_c` 用 100，`steep_min` 不少于 20，`refill_times` 写 0，
     步骤里要写明「煮开后转小火煮 20–30 分钟」。
   - 香气类饮片（薄荷、藿香、紫苏、玫瑰花、菊花、茉莉花）与枸杞子**不要久煮**，最后 2–3 分钟放入。
   - 两类同时出现时，先煮其余饮片，最后 2–3 分钟再下香气类。
```

**(c) 修掉反例**：`agent2_system.md:64` 的示例含茯苓，必须改。
建议**拆成两个示例**（一个冲泡、一个煎煮），既去掉反例，又给模型一个正面范式：

- 示例 1（冲泡）：把茯苓换成不必煎煮的（如「陈皮＋山楂＋荷叶」），保持原来的痰湿质＋麻辣烫场景；
- 示例 2（煎煮，新增，短）：输入「脾虚湿重、吃了冰饮」，输出「茯苓＋山药＋莲子」用养生壶煮 20–30 分钟。

#### 第 3 层 · 兜底路径：`COOK_BREW`

`matcher.py` 在 `DEFAULT_BREW` 旁新增：

```python
COOK_BREW = BrewGuide(
    vessel="养生壶或小锅",
    water_ml=600,
    water_temp_c=100,
    steps=[
        "原料温水快速冲洗，质地坚硬的先浸泡 20 分钟",
        "放入壶中，加约 600 ml 清水煮开",
        "转小火煮 20–30 分钟，豆类与薏苡仁须彻底熟透",
        "温热饮用，当天喝完不留隔夜",
    ],
    steep_min=30,
    refill_times=0,
)
```

选择逻辑：`_blend_needs_cooking(blend)`（读 `requires_cooking` 标记）为真时用 `COOK_BREW`，
并在 `Basis.rule_hits` 里加一条 `brew_cook_required`，让事后归因看得出为什么换方式。

参数校验：`BrewGuide` 限 `steep_min ∈ [1,60]`、`water_temp_c ∈ [40,100]`、`refill_times ∈ [0,5]`（`models.py`）——
`steep_min=30` / `temp=100` / `refill=0` 全部合法，**无需改模型**。

#### 第 4 层 · 护栏：模型答错时兜住

`orchestrator._sanitize_recommendations()` 的循环里已经拿得到 `rec.brew`（`check_blend` 只看 herbs），
所以**不必改 `check_blend` 的签名**，新增一个并列的检查即可：

```python
# app/domain/safety.py
def check_brew_adequacy(herbs: list[dict], brew) -> GuardrailResult:
    """搭配里有必须煎煮的饮片，而冲泡方式仍是焖泡时报警并给出改法。"""
```

- 触发判据：blend 含 `requires_cooking` 标记的味，且（`brew.steep_min < 20` 或 `water_temp_c < 100` 或
  `vessel` 不含「壶/锅」）。
- **处置建议：自动换用 `COOK_BREW` 并把原因记进 `guardrail_applied`**（形如
  「茯苓：须煎煮，已由闷泡改为养生壶煮 20–30 分钟」）。
  **理由**：这与既有的剂量处理同构 —— `check_blend` 对超限用量就是「裁剪 + 记进 `adjusted`」，
  项目原则是「不**静默**丢弃/改写」，而不是「不许改写」。若你更倾向只报警不改写，说一声即可（两条路都留了位置）。

### 6.2　两处偏离方案的理由（都是实测后收窄）

**① B（默认搭配避开）只落在痰湿质一处，其余三处保留并走煎煮。**
§2.4 的 B 写的是「默认搭配尽量避开」，但逐个查候选集后只有一处做得到：

| 默认搭配 | 含须煎煮味 | 有无等价替代 | 处置 |
|---|---|---|---|
| `CONSTITUTION_DEFAULT` 痰湿质 | 茯苓 8g | **有** —— 陈皮 5 + 荷叶 5，两味都在痰湿质的 suitable 段 | **换掉**（`陈皮荷叶化湿饮`） |
| `CONSTITUTION_DEFAULT` 特禀质 | 山药 10g | **没有** —— 平补固表方向只有「红枣、山药」两味 suitable，山药无替代 | 保留，走 `COOK_BREW` |
| `RULES.sweet_heavy` | 茯苓 6g | 有，但两处同时换成同一组会让「甜腻餐后」与「痰湿体质」给出完全一样的搭配 | 保留，走 `COOK_BREW` |
| `RULES.late_night` | 茯苓 6g | **没有** —— 「和胃安神」依赖茯苓的宁心，白名单内无非煎煮等价物 | 保留，走 `COOK_BREW` |

⇒ **用户可察觉的变化**：痰湿质默认由「茯苓陈皮化湿饮」变为「**陈皮荷叶化湿饮**」（仍是保温杯焖泡）；
特禀质默认（山药红枣）与规则 `sweet_heavy` / `late_night` 的冲泡方式改为「养生壶煮 20–30 分钟」。
**这三处可感知变化是本方案最大的一笔代价。** 要改回去时读 `matcher.py` 末尾的「默认搭配选择纪律」，
`test_phlegm_damp_default_avoids_cook_required` 会提示。

**② 独立佐证：`docs/whitelist-expansion-scan.md` §0.3 早就得出同一份 6 味清单。**
那份扫描稿从「泡水 vs 煎服」的口径冲突出发，列出的正是茯苓、山药、薏苡仁、白扁豆、莲子、百合 ——
与本次逐条读 `brewing` 的结论**完全一致**。两条独立路径同一结论，提高这份清单的可信度。

### 6.3　已知代价
